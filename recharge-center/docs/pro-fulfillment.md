# Pro 5x / Pro 20x 履约说明

## 使用

部署后沿用原有 `/admin/login` 会话、7 天设备记忆、CSRF 和退出机制。进入 `/admin/cards`，选择 Plus、Pro 5x 或 Pro 20x 生成卡密。历史 HPLUS 卡缺少 `plan` 时按 Plus 解释。Pro 20x 始终进入人工队列。

在 `/admin/pro-orders` 查看 Pro 订单，按套餐、履约方式、状态筛选；点“打开”复制加密保存的原始 JSON、记录备注、标记人工处理中/需补资料，并在外部实际完成充值后点击“确认人工充值成功”。该按钮只修改本站订单与卡密，不调用嗨付接口。确认弹窗显示账号、套餐和订单号。成功订单的原始资料沿用现有 45 天清理策略。

Pro 5x 自动充值默认关闭。根据运营提供的“约 $93 扣款、卡内留 $100”，新安装的默认配置为预计扣款 $93 + 额外安全余额 $7，提交前要求指定卡可用余额至少 $100；实际扣款可能浮动，$100 不是支付成功保证。在后台先同步卡片列表，选一张卡，核对计费地区（默认推荐 EG）及金额，再开启开关。未指定卡或预计扣款额为 0 无法开启。选中卡无论开关状态如何都从 Plus 自动选卡池隔离；已有 Pro 续费保护卡不用于新 Pro 订单。`region` 是计费地区；代理节点沿用服务端现有 `HIFUPAY_PROXY_REGION`，两者不能混用。

订单创建时保存套餐、初始履约方式、指定卡与计费配置快照；后续修改设置不改变旧订单。Pro 5x 自动订单逐笔占用指定卡，提交前再刷新卡片余额和状态；不可用则转人工，不换备用卡。请求发起前持久化 `submitting` 与占用，拿到 taskId 立即保存；不明确的响应或进程中断进入待确认，保留占用，绝不自动重发。重启后只查询已保存 taskId 的任务；未知 taskId 不自动补单。支付成功与关闭自动续费分别记账，关闭续费失败不视为支付失败。

“核实未扣款并转人工”需要运营填写核查依据，确认原任务未扣款且未成功；无 taskId 时还要核查上游未受理，并通过实时余额未变化校验。有 taskId 时必须收到上游终止、明确未扣款结果，间隔至少 `HIFUPAY_FAILURE_CONFIRM_SECONDS` 两次核验，并通过实时余额未变化校验。无法确认时保持待确认与占用，不可人工再充。服务器只能校验上游接口与余额；人工核查上游平台记录属于运营责任。

## 验证与发布

本地在 `recharge-center/` 运行 `npm test`。集成测试使用临时 JSON 数据和本地模拟服务；不应使用真实 API Key 测试自动充值。部署前备份生产 `orders.json` 与环境文件，先确认服务仍为单实例、数据卷持久化及加密密钥不变。可按现有 `.github/workflows/deploy-vps.yml` 的测试/部署流程发布；本任务未执行线上部署或真实扣款。上线后先保持自动开关关闭，验证后台会话、卡密生成、人工订单、原始 JSON、状态查询以及 Plus 回归；再由运营核对 $93 / $7 与实际卡片余额、指定卡后开启自动模式。勿修改购买链接锁、provider 配置或凭据。若数据文件已保存过 Pro 5x 金额设置，保留已保存值；新增默认值不会覆盖它，须在后台核对或修改。

回滚时先关闭 Pro 5x 自动开关、停止新 Pro 卡销售并备份 `orders.json`；若有 `submitting`、`processing` 或 `needs_review` 订单，先核查并保留占用，不能用旧服务重新提交。代码回退后旧服务不会处理 Pro 队列；应保留数据和原有加密密钥，修复后前滚恢复。不要删除订单、卡密或占用记录。上线成功与否以生产健康检查和人工验收为准，本地测试不等于线上生效。

# 吱吱鼠 Plus：本地实现与上线门槛

接口核对日期：2026-09-22，来源：[公开 API 文档](https://card.zzshu.pro/docs)。`POST /api/v1/third-party/orders/direct` 使用 `orderType=direct`、`planType=plus` 和完整 Session JSON；不显式传 region，文档默认 PH。`201/code=0` 只表示创建，保存 `order_no` 和 `card_key` 后用 `POST /api/v1/third-party/orders/status` 查询。响应包含 `bank_card_no`、`token`，适配器只提取订单号、状态、支付结果、是否要求持卡人验证和取消续费标志，绝不返回验证密钥。文档没有明确可依赖的卡头白名单或余额查询能力；格式预检不等于支持扣款。5X 与 Plus 升 5X 均未实现。

支付卡池统一入口为 `/admin/hifupay/cards`。同一列表展示嗨付来源卡和手动导入卡、适用协议、总次数、已用、冻结及剩余次数。嗨付来源卡的使用次数在嗨付和 ZZS 之间共用；手动导入卡目前只能由 ZZS 使用，因为嗨付接口要求平台卡 ID。后台可同步嗨付卡、调整其轮选顺序与总次数，也可导入和管理手动卡。支付结果不明时先冻结本次次数，其余次数仍可接新订单；管理员核实后在订单页决定释放或记为消耗。客户卡密的协议路由和旧订单 provider 约束不因卡池合并而改变。手动卡不要重复粘贴已有嗨付来源卡。

新 Plus 卡密从 `/admin/cards` 统一生成，在 `/admin` 选择“通用 Plus 卡密充值通道”：嗨付或 ZZS。尚未提交的新通用卡密按当前设置路由；首次有效提交时持久化该卡密选定的通道，后续切换只影响其他未提交卡密。旧 HPLUS 卡密仍固定走嗨付，旧 ZZPLUS 卡密仍固定走 ZZS；Pro 卡密保持原处理。通用卡密登记在两套存储中，不能只备份其中一个。旧卡密生成接口仍保留兼容；支付卡池页只负责卡片管理，订单明细统一在 `/admin/recoveries`。

环境变量示例见 `.env.example`。保持 `DEFAULT_PROVIDER` 原值，显式 `ZZSHU_ENABLED=true` 才可能下单。SQLite 文件 `ZZSHU_DB_FILE` 默认与 `DATA_FILE` 同目录；备份时必须同时备份 SQLite 和 WAL，并保留固定 `ZZSHU_API_KEY`、`RECOVERY_ENCRYPTION_KEY`，否则历史查询/卡密不可恢复。仅单机或共享本地 SQLite 文件系统支持这里的事务语义；多机不共享文件系统时必须迁移到集中事务库。Node.js 22 的 `node:sqlite` 在当前运行时为实验特性，上线前固定并验证部署版本。

## ZZS API 凭据配置

当部署环境没有 `ZZSHU_API_KEY` 时，管理员可在 `/admin` 的 ZZS API 区粘贴 ZZS 发放的固定 API Key 或卡密。提交时仅调用 `GET /api/v1/third-party/user` 验证；通过后才以 `RECOVERY_ENCRYPTION_KEY` 加密写入运行时的独立私密文件（默认 `DATA_FILE` 同目录下的 `zzshu-api-key.json`，权限 `0600`）。页面和管理 API 只返回“已配置/未配置”及验证后的剩余点数，绝不回显 Key。

ZZS 历史订单保存在本站服务器，后台查看不依赖当前 API Key。上游查单仍按创建时的 Key 归属；更换 Key 后，旧的未完成订单保留在本站并进入待核查，不会使用新 Key 自动查单、重发或自动确认成功。连接检测会显示上游 HTTP 状态和数字错误码。充值订单详情显示最近一次查单时间、分类结果、HTTP 状态及上游数字错误码，不保存上游响应正文中的 Session 或卡片资料。只有查单明确证实已付款，本站才核销卡密和记一次支付卡成功；取消续费未确认时另行提示核查。

新 ZZS 订单在预留支付卡前，先使用已保存的 Key 调用只读账号接口。上游网关异常或 Key 验证失败时直接返回“尚未提交”，不创建订单、不占支付卡、不核销客户卡密；已有订单按原订单号继续查询，不会重新提交。后台“诊断上游连通性”用故意无效的测试 Key 比较默认、浏览器请求头、IPv4 和 IPv6；正常应收到 `40107`，若均返回网关错误，则问题与真实 Key 内容无关。

后台总览的“ZZS 开通记录”通过 ZZS 文档公开的只读 `/api/v1/third-party/orders/history` 接口，服务端带已保存的 Key 分页查询。界面只显示时间、账号、套餐、开通与续费状态、扣点及任务号；不透传上游原始响应、Key 或支付资料。订单详情提供入口，管理员可对照本站上游订单号和账号。此查询不会改变本站订单；若需同步状态，仍使用原订单的查单流程。

保存凭据不会设置 `ZZSHU_ENABLED`、不会创建订单、不会变更默认 provider 或分配支付卡。后台更换 Key 时暂停新充值提交；验证成功后允许更换，旧订单留在本地，未完成订单转为待核查并冻结其支付卡次数，成功订单停止使用新 Key 查询续费状态。数据库记录当前查询 Key 的指纹，重启后仍阻止新 Key 查旧单。已验证的后台替换 Key 会加密保存并优先于部署环境 Key；未执行后台替换时继续使用部署环境 Key。

## 支付卡与手动导入

嗨付公开[API 文档](https://cdk.hifupay.com/api-docs.html)列出 `POST /api/hfp/card-sensitive`：嗨付来源的卡仅在某笔吱吱鼠订单提交前按该卡的平台 ID 获取完整资料，并校验尾号和有效期，随后直接构造吱吱鼠 `direct` 请求；不缓存、不进入 SQLite/JSON/日志/客户响应。嗨付卡列表接口返回的额外敏感字段在适配器入口剔除。手动来源的卡采用下述加密持久化路径，两类卡的资料处理方式不同。

管理员在 `/admin/hifupay/cards#importPanel` 可一次粘贴多行 `卡号,MM/YY,CVV`。新导入的完整资料（含 CVV）使用 `RECOVERY_ENCRYPTION_KEY` 加密后持久化在 `ZZSHU_DB_FILE` 的 `payment_cipher` 字段；自动下单时按卡片引用解密。预览、导入结果、管理接口和客户接口只显示尾号，不返回完整资料或密文。重复卡按卡号指纹跳过，不改变原卡的成功次数或总次数。旧版外部 Vault 引用仍按原配置读取，新导入不依赖 `ZZSHU_VAULT_URL` / `ZZSHU_VAULT_TOKEN`。备份数据库时须保留原加密密钥，否则手动卡无法解密。

**上线限制：**PCI SSC 的 [FAQ 1280](https://www.pcisecuritystandards.org/faqs/1280/) 明确说明，CVV 不能在交易授权后为未来交易保留，即使加密也不行。因此本地实现满足所要求的自动复用流程和测试验收，但该持久化 CVV 路径不应直接用于真实支付；上线前需由收单方/支付通道确认无需保存 CVV 的重复支付方式，或更换有合规授权的支付凭据方案。页面脱敏与加密不能解除这项限制。

手动卡默认总次数为 1，剩余次数等于总次数减去成功与冻结次数；修改总次数不清空成功历史。已使用且仍有次数的卡优先，之后按导入顺序选下一张。占用、停用、暂停和耗尽的卡不能选；SQLite 唯一索引保护同一张卡的未决占用。嗨付来源卡仍需满足相应协议的余额与状态要求。

手动卡可在卡池点击“移出卡池”。有未完成订单占用时操作被拒绝；其余卡移出后会从卡池消失，支付资料和备注被清除，且不能再启用或自动选中。卡片指纹和历史成功次数仍保留在数据库，以防重复导入同一张卡并保留旧订单关联。嗨付来源的卡在同一列表中管理，不使用此按钮。

统一卡池中每张手动卡可展开查看已成功充值的账号、账号 ID 和订单提交时间。同一账号多次成功充值会保留多条记录；处理中或待核查账号单独标注，不计入成功记录。资料直接来自本站订单数据库，不依赖上游 API 可用。删除卡片后，该卡不再出现在可用卡池，旧订单记录仍可在充值订单页查询。

“无可用卡”不会预留客户兑换卡密。创建响应丢失、超时、未知状态以及上游失败但支付状态不明会冻结本次使用次数待确认；管理员明确选择“冻结待查”后，相关支付卡也停止接收新订单，直到人工解锁或确认成功。失败即使报告 `payment_result.status=failed` 也不自动释放，因为公开文档没有给出足够强的“绝不扣款”保证；后台可在核实后人工结案。人工确认为未支付后，原订单保留为失败历史，兑换卡密恢复未使用状态，可再次提交。成功计数和卡密核销在同一 SQLite 事务里只发生一次。上游没有下游幂等键，不应按本地订单号自动补发创建请求。
创建前明确拒绝的 `42902`、`40305`、API 凭据及 Session 校验错误会保留本地失败历史，释放支付占用及客户卡密权益，不自动重新下单。用户 token 失效与本站 API 凭据失效分别提示；有上游订单标识或支付结果的响应不能按创建前拒绝释放。状态查询若返回非空 `verification`，订单冻结本次次数并提示需要持卡人验证；不会把 `client_secret` 返回给客户或普通管理接口，也不会换卡重新下单。
服务重启后，超过两倍接口超时（至少 30 秒）的预留中或提交中订单会转为待确认并留下审计记录，冻结本次次数；没有上游 `card_key` 的单不会自动补查或重发。已有查询标识的订单轮流补查，避免旧订单长期占满轮询名额。

管理员订单页展示具体核查原因；没有上游查询标识的待确认订单只提供人工核实结果，不会显示无效的补查按钮。人工确认成功、解锁、冻结待查与确认续费已关闭均使用预设核查依据及选填备注，并记录管理会话、时间和状态变化；无需手填 8 字，重复操作不会再次扣次数。订单页可查询全部本站订单，已保存的 JSON 可按单复制；读取订单不再自动按 45 天删除 JSON，先前已清理的内容无法恢复。

上线前请确认嗨付卡详情向吱吱鼠使用的许可与合规依据、固定的双通道 API Key 安全配置、`RECOVERY_ENCRYPTION_KEY`、生产备份/监控方案，并确认人工未支付判定责任。上线后先用上游提供的安全沙箱或非扣款演练验证端到端，不能用真实卡/Session 做本地测试。


### 客户账号绑定与页面恢复

本站生成的客户卡密在首次有效确认提交时绑定邮箱及账号 ID。失败、支付资料读取失败、无可用支付卡，以及嗨付后台解锁，都不能清除绑定或换账号；未支付不核销兑换权益，原账号仍按原有重试规则处理。无效 JSON 不绑定。ZZS 历史失败订单若保留账号记录，会在下一次提交时恢复校验；历史资料已被清除且无可追溯记录的卡密无法凭空恢复原账号。

Plus 激活链接打开时先查询本站卡密状态，已提交或完成的卡密直接显示查询结果。提交响应丢失时仅查询，不自动重新下单；浏览器当前会话只保存待确认标记，不保存 JSON。若始终没有可确认的订单，客户需要联系客服核查。成功结果将确认按钮更新为“充值已完成”。

结果不明时客户页显示正在核查，不允许重复提交。明确未受理或管理员核实未开通、未扣款并解锁后，客户页允许原卡密为原账号重新提交；授权失效时提示获取新的 Session JSON，提供更新资料入口。后台保留原订单、返回原因及核查记录。若请求在创建订单前就被拒绝，例如卡密无效，则客户页明确提示“暂未完成提交”，不声称已经排队。历史失败订单再次打开激活链接时，根据明确的重试授权显示更新资料或待核查提示，页面不会自动再次提交。

### 客户卡密与订单检索

卡密库支持输入客户卡密任意片段、尾号、绑定账号或完整激活链接；尾号重复时显示全部匹配卡密。每张卡提供复制充值链接、查看关联订单和复制 JSON。复制 JSON 优先取最新成功订单；没有成功订单时取最近一次提交，所选订单没有留存 JSON 时明确显示“未留存 JSON”。

从卡密库进入订单页时按客户卡密 ID 展示全部关联订单。订单页将客户兑换卡密与实际支付卡尾号分开显示，并可搜索客户卡密片段或支付卡尾号。历史 ZZS 独立卡密若仍有加密凭据则显示原卡密；无法恢复时标为“历史卡密未关联”，不把支付卡尾号误标为客户卡密。


## 充值接口返回历史

创建充值订单及每次查单的响应，在解析完成、改变订单状态之前，追加到 SQLite `response_history`。包含请求阶段、返回时间、HTTP 状态、业务错误码、嵌套错误说明及状态；成功、拒绝、未知业务码均保存，连接失败和非 JSON 响应也留下独立记录。保存历史不会改变结案或卡密释放规则。

只保留说明和状态字段，过滤 Session、token、API Key、上游 card_key、完整支付卡号、CVV、验证凭据及说明中可识别的敏感值；不保存整个上游原始响应、请求体或 HTML 页面。用户接口不会返回历史。管理员在充值订单的“详情 → ZZS 返回历史”查看，按最新在前排列，每页 100 条，可刷新或加载更早记录。管理员接口为 `GET /api/admin/recoveries/:id/responses?before=:cursor`，需要管理会话。历史采用追加记录，不因补查、重启或人工结案而覆盖；上线前丢失的说明无法回填。


## ZZS 人工恢复与用户重试（2026-10-02）

- 订单详情提供“解锁卡密”“冻结待查”“确认充值成功”。解锁要求管理员选择已经核实未开通、未扣款的依据；原订单保留为失败，原卡密继续绑定原账号。成功操作核销卡密并计一次成功，不调用充值接口。
- 冻结待查不是永久作废。客户卡密和相关支付占用保留；可补查原订单，但人工冻结后补查不会自动结案，管理员仍需解锁或确认成功。有上游查询标识且查询 Key 仍有效时才提供安全补查，没有标识时明确提示人工核查。
- 核查弹窗显示账号、订单、卡密尾号和操作效果，核查依据必选，备注选填。结构化依据由服务端校验并生成审计内容，记录管理会话标识和操作前后状态；旧接口保留兼容，新后台不要求手填 8 字。
- 自动流程明确返回用户授权失效（现有 Session 失效码 `40027`，或业务 `401` 配合明确的 token 失效说明），且没有上游订单标识及支付结果时，保存脱敏返回并释放卡密与支付占用。通用 HTTP 401 不足以判定用户 token 失效；API 凭据错误不要求用户更新 JSON。未知错误仍进入待核查。
- 用户只收到更新资料、服务暂不可用、正在处理、正在核查或成功等可执行提示；不透传上游码和报错。原卡密的重试权限贯穿提交、卡密查询和订单查询；提交响应丢失后，也能通过查询恢复已批准的重试入口。重试需要用户主动提交新的 JSON，系统不自动重下单。
- 管理员复制 JSON 到 ZZS 后台进行的操作不会自动回传本站。可选择“已人工核实授权失效且未开通未扣款”解锁，本站提示用户更新 Session。没有本地上游任务的历史提交也可冻结、解锁或确认成功。
- 服务端拒绝解锁成功订单、操作已被新提交替代的旧订单，以及在提交仍进行时结案。卡密核销、支付次数和本地审计在 SQLite 同一事务完成；JSON 中的提交展示状态通过原生订单同步恢复。

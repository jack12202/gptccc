# 吱吱鼠 Plus：本地实现与上线门槛

接口核对日期：2026-09-18，来源：[公开 API 文档](https://card.zzshu.pro/docs)。`POST /api/v1/third-party/orders/direct` 使用 `orderType=direct`、`planType=plus` 和完整 Session JSON；不显式传 region，文档默认 PH。`201/code=0` 只表示创建，保存 `order_no` 和 `card_key` 后用 `POST /api/v1/third-party/orders/status` 查询。响应包含 `bank_card_no`、`token`，适配器只提取订单号、状态、支付结果和取消续费标志。文档没有明确可依赖的卡头白名单或余额查询能力；格式预检不等于支持扣款。5X 与 Plus 升 5X 均未实现。

嗨付卡池页 `/admin/hifupay/cards` 已直接显示卡片用途：刷新嗨付卡片后，展开指定卡片，点“分配给吱吱鼠 Plus”或“改回嗨付”。顶部按钮可进入独立的 `/admin/zzshu` 管理页；两处使用同一套分配记录和服务端校验。新卡默认仍归嗨付；只要没有未决嗨付/吱吱鼠订单且没有 Pro 保护，管理员可以手动把卡分配给吱吱鼠。已有嗨付成功记录和账号关联继续保留，但不阻止改变未来用途。分配给吱吱鼠的卡不再进入嗨付自动选卡；两条执行通道共用 SQLite 卡片用途与未决占用闸门。吱吱鼠 Plus 成功上限默认 5 次，可在支付卡池调整。原有逐行粘贴导入仍保留给非嗨付来源，但需另配受控凭据服务，不要把同一张嗨付卡再粘贴一遍。生成客户卡密时固定 Plus 与 `zzshu`，复制链接交付；卡密库和订单页查看绑定账号、状态、卡尾号、取消续费。订单“安全补查”只用已保存的上游 `card_key`；缺少该标识时不得自动重下单。人工结案只能对待确认单选择“确已成功”或“明确未支付”，必须留下至少 8 字审计依据。人工判未支付会解除支付卡占用，操作前须独立核验支付平台及上游记录。已成功订单的取消续费若未确认会继续补查，但不再次开通或计数。

环境变量示例见 `.env.example`。保持 `DEFAULT_PROVIDER` 原值，显式 `ZZSHU_ENABLED=true` 才可能下单。SQLite 文件 `ZZSHU_DB_FILE` 默认与 `DATA_FILE` 同目录；备份时必须同时备份 SQLite 和 WAL，并保留固定 `ZZSHU_API_KEY`、`RECOVERY_ENCRYPTION_KEY`，否则历史查询/卡密不可恢复。仅单机或共享本地 SQLite 文件系统支持这里的事务语义；多机不共享文件系统时必须迁移到集中事务库。Node.js 22 的 `node:sqlite` 在当前运行时为实验特性，上线前固定并验证部署版本。

## 支付凭据待确认

GPTC **不存储**完整卡号和 CVV。嗨付公开[API 文档](https://cdk.hifupay.com/api-docs.html)列出 `POST /api/hfp/card-sensitive`：本实现仅在某笔吱吱鼠订单提交前按已分配卡的 ID 获取完整资料，并校验尾号和有效期，随后直接构造吱吱鼠 `direct` 请求；不缓存、不进入 SQLite/JSON/日志/客户响应。嗨付卡列表接口返回的额外敏感字段在适配器入口剔除。此技术路径不等于对发卡方及持卡数据处理的合规背书：上线前必须核实嗨付允许将其卡片详情用于第三方执行通道，并确认其提供 CVV 的业务/合规依据。尤其不能为未来交易自行长期保存 CVV。

对于**非嗨付来源**的粘贴导入，仍需配置受控服务 `ZZSHU_VAULT_URL`（HTTPS）及 `ZZSHU_VAULT_TOKEN`，提供 `POST /credentials` 和 `GET /credentials/{ref}`；不能把长期保存 CVV 搬到另一个普通数据库，且不可用加密字段伪装合规。若无经过确认的按次凭据供应方式，不应使用这个导入入口。

“无可用卡”不会预留客户兑换卡密。创建响应丢失、超时、未知状态以及上游失败但支付状态不明均保留占用待确认。失败即使报告 `payment_result.status=failed` 也不自动释放，因为公开文档没有给出足够强的“绝不扣款”保证；后台可在核实后人工结案。成功计数和卡密核销在同一 SQLite 事务里只发生一次。上游没有下游幂等键，不应按本地订单号自动补发创建请求。
服务重启后，超过两倍接口超时（至少 30 秒）的预留中或提交中订单会转为待确认并留下审计记录，继续占用卡片；没有上游 `card_key` 的单不会自动补查或重发。已有查询标识的订单轮流补查，避免旧订单长期占满轮询名额。

上线前请确认嗨付卡详情向吱吱鼠使用的许可与合规依据、固定的双通道 API Key 安全配置、`RECOVERY_ENCRYPTION_KEY`、生产备份/监控方案，并确认人工未支付判定责任。上线后先用上游提供的安全沙箱或非扣款演练验证端到端，不能用真实卡/Session 做本地测试。

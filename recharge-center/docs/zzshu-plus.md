# 吱吱鼠 Plus：本地实现与上线门槛

接口核对日期：2026-09-22，来源：[公开 API 文档](https://card.zzshu.pro/docs)。`POST /api/v1/third-party/orders/direct` 使用 `orderType=direct`、`planType=plus` 和完整 Session JSON；不显式传 region，文档默认 PH。`201/code=0` 只表示创建，保存 `order_no` 和 `card_key` 后用 `POST /api/v1/third-party/orders/status` 查询。响应包含 `bank_card_no`、`token`，适配器只提取订单号、状态、支付结果、是否要求持卡人验证和取消续费标志，绝不返回验证密钥。文档没有明确可依赖的卡头白名单或余额查询能力；格式预检不等于支持扣款。5X 与 Plus 升 5X 均未实现。

嗨付卡池页 `/admin/hifupay/cards` 已直接显示卡片用途：刷新嗨付卡片后，展开指定卡片，点“分配给吱吱鼠 Plus”或“改回嗨付”。ZZS 手动卡池位于 `/admin/hifupay/cards?tab=zzshu`；两处使用同一套分配记录和服务端校验。新卡默认仍归嗨付；只要没有未决嗨付/吱吱鼠订单且没有 Pro 保护，管理员可以手动把卡分配给吱吱鼠。已有嗨付成功记录和账号关联继续保留，但不阻止改变未来用途。分配给吱吱鼠的卡不再进入嗨付自动选卡；两条执行通道共用 SQLite 卡片用途与未决占用闸门。嗨付来源的吱吱鼠 Plus 成功上限默认 5 次，可在支付卡池调整；手动导入默认 1 次。手动卡可逐行粘贴导入，不要把同一张嗨付卡再粘贴一遍。订单“安全补查”只用已保存的上游 `card_key`；缺少该标识时不得自动重下单。人工结案只能对待确认单选择“确已成功”或“明确未支付”，必须留下至少 8 字审计依据。人工判未支付会解除支付卡占用，操作前须独立核验支付平台及上游记录。已成功订单的取消续费若未确认会继续补查，但不再次开通或计数。

新 Plus 卡密从 `/admin/cards` 统一生成，在 `/admin` 选择“通用 Plus 卡密充值通道”：嗨付或 ZZS。尚未提交的新通用卡密按当前设置路由；首次有效提交时持久化该卡密选定的通道，后续切换只影响其他未提交卡密。旧 HPLUS 卡密仍固定走嗨付，旧 ZZPLUS 卡密仍固定走 ZZS；Pro 卡密保持原处理。通用卡密登记在两套存储中，不能只备份其中一个。旧卡密生成接口仍保留兼容；支付卡池页只负责卡片管理，订单明细统一在 `/admin/recoveries`。

环境变量示例见 `.env.example`。保持 `DEFAULT_PROVIDER` 原值，显式 `ZZSHU_ENABLED=true` 才可能下单。SQLite 文件 `ZZSHU_DB_FILE` 默认与 `DATA_FILE` 同目录；备份时必须同时备份 SQLite 和 WAL，并保留固定 `ZZSHU_API_KEY`、`RECOVERY_ENCRYPTION_KEY`，否则历史查询/卡密不可恢复。仅单机或共享本地 SQLite 文件系统支持这里的事务语义；多机不共享文件系统时必须迁移到集中事务库。Node.js 22 的 `node:sqlite` 在当前运行时为实验特性，上线前固定并验证部署版本。

## ZZS API 凭据配置

当部署环境没有 `ZZSHU_API_KEY` 时，管理员可在 `/admin` 的 ZZS API 区粘贴 ZZS 发放的固定 API Key 或卡密。提交时仅调用 `GET /api/v1/third-party/user` 验证；通过后才以 `RECOVERY_ENCRYPTION_KEY` 加密写入运行时的独立私密文件（默认 `DATA_FILE` 同目录下的 `zzshu-api-key.json`，权限 `0600`）。页面和管理 API 只返回“已配置/未配置”及验证后的剩余点数，绝不回显 Key。

保存凭据不会设置 `ZZSHU_ENABLED`、不会创建订单、不会变更默认 provider 或分配支付卡。为保留旧订单的上游查询归属，后台更换 Key 时会暂停新充值提交，并拒绝在有处理中、待核查或续费关闭待同步订单时替换；这些订单处理完毕后方可更换。已验证的后台替换 Key 会加密保存并优先于部署环境 Key，服务重启后仍生效；未执行后台替换时继续使用部署环境 Key。

## 支付卡与手动导入

嗨付公开[API 文档](https://cdk.hifupay.com/api-docs.html)列出 `POST /api/hfp/card-sensitive`：嗨付来源的卡仅在某笔吱吱鼠订单提交前按已分配卡的 ID 获取完整资料，并校验尾号和有效期，随后直接构造吱吱鼠 `direct` 请求；不缓存、不进入 SQLite/JSON/日志/客户响应。嗨付卡列表接口返回的额外敏感字段在适配器入口剔除。手动来源的卡采用下述加密持久化路径，两类卡的资料处理方式不同。

管理员在 `/admin/hifupay/cards?tab=zzshu#manual-card-import` 可一次粘贴多行 `卡号,MM/YY,CVV`。新导入的完整资料（含 CVV）使用 `RECOVERY_ENCRYPTION_KEY` 加密后持久化在 `ZZSHU_DB_FILE` 的 `payment_cipher` 字段；自动下单时按卡片引用解密。预览、导入结果、管理接口和客户接口只显示尾号，不返回完整资料或密文。重复卡按卡号指纹跳过，不改变原卡的成功次数或总次数。旧版外部 Vault 引用仍按原配置读取，新导入不依赖 `ZZSHU_VAULT_URL` / `ZZSHU_VAULT_TOKEN`。备份数据库时须保留原加密密钥，否则手动卡无法解密。

**上线限制：**PCI SSC 的 [FAQ 1280](https://www.pcisecuritystandards.org/faqs/1280/) 明确说明，CVV 不能在交易授权后为未来交易保留，即使加密也不行。因此本地实现满足所要求的自动复用流程和测试验收，但该持久化 CVV 路径不应直接用于真实支付；上线前需由收单方/支付通道确认无需保存 CVV 的重复支付方式，或更换有合规授权的支付凭据方案。页面脱敏与加密不能解除这项限制。

手动卡默认总次数为 1，剩余次数等于总次数减去成功次数；修改总次数不清空成功历史。已使用且仍有次数的卡优先，之后按导入顺序选下一张。占用、停用、暂停和耗尽的卡不能选；SQLite 唯一索引保护同一张卡的未决占用。该次数规则不改变嗨付卡的余额选择逻辑。

手动卡可在卡池点击“移出卡池”。有未完成订单占用时操作被拒绝；其余卡移出后会从卡池消失，支付资料和备注被清除，且不能再启用或自动选中。卡片指纹和历史成功次数仍保留在数据库，以防重复导入同一张卡并保留旧订单关联。嗨付来源的卡须在嗨付卡分配区管理，不使用此按钮。

ZZS 手动卡池中每张卡可展开查看已成功充值的账号、账号 ID 和订单提交时间。同一账号多次成功充值会保留多条记录；处理中或待核查账号单独标注，不计入成功记录。资料直接来自本站订单数据库，不依赖上游 API 可用。删除卡片后，该卡不再出现在可用卡池，旧订单记录仍可在充值订单页查询。

“无可用卡”不会预留客户兑换卡密。创建响应丢失、超时、未知状态以及上游失败但支付状态不明均保留占用待确认。失败即使报告 `payment_result.status=failed` 也不自动释放，因为公开文档没有给出足够强的“绝不扣款”保证；后台可在核实后人工结案。人工确认为未支付后，原订单保留为失败历史，兑换卡密恢复未使用状态，可再次提交。成功计数和卡密核销在同一 SQLite 事务里只发生一次。上游没有下游幂等键，不应按本地订单号自动补发创建请求。
上游文档明确为创建前拒绝的 `42902`、`40305`、API 凭据及 Session 校验错误会保留本地失败历史，同时释放卡片和客户卡密，不自动重试。状态查询若返回非空 `verification`，订单保留占用并提示需要持卡人验证；不会把 `client_secret` 返回给客户或普通管理接口，也不会换卡重新下单。
服务重启后，超过两倍接口超时（至少 30 秒）的预留中或提交中订单会转为待确认并留下审计记录，继续占用卡片；没有上游 `card_key` 的单不会自动补查或重发。已有查询标识的订单轮流补查，避免旧订单长期占满轮询名额。

管理员订单页展示具体核查原因；没有上游查询标识的待确认订单只提供人工核实结果，不会显示无效的补查按钮。人工确认成功、明确未支付与确认续费已关闭均记录核查依据；重复操作不会再次扣次数。订单页可查询全部本站订单，已保存的 JSON 可按单复制；读取订单不再自动按 45 天删除 JSON，先前已清理的内容无法恢复。

上线前请确认嗨付卡详情向吱吱鼠使用的许可与合规依据、固定的双通道 API Key 安全配置、`RECOVERY_ENCRYPTION_KEY`、生产备份/监控方案，并确认人工未支付判定责任。上线后先用上游提供的安全沙箱或非扣款演练验证端到端，不能用真实卡/Session 做本地测试。


### 客户账号绑定与页面恢复

本站生成的客户卡密在首次有效确认提交时绑定邮箱及账号 ID。失败、支付资料读取失败、无可用支付卡，以及嗨付后台解锁，都不能清除绑定或换账号；未支付不核销兑换权益，原账号仍按原有重试规则处理。无效 JSON 不绑定。ZZS 历史失败订单若保留账号记录，会在下一次提交时恢复校验；历史资料已被清除且无可追溯记录的卡密无法凭空恢复原账号。

Plus 激活链接打开时先查询本站卡密状态，已提交或完成的卡密直接显示查询结果。提交响应丢失时仅查询，不自动重新下单；浏览器当前会话只保存待确认标记，不保存 JSON。若始终没有可确认的订单，客户需要联系客服核查。成功结果将确认按钮更新为“充值已完成”。

已创建订单但后台确认未成功时，客户页显示“已提交，等待处理”，提示等候过久联系人工；后台仍保留真实失败状态和原因。若请求在创建订单前就被拒绝，例如卡密无效，则客户页明确提示“暂未完成提交”，不声称已经排队。历史失败订单再次打开激活链接时也进入等待人工处理提示，页面不会自动再次提交。

### 客户卡密与订单检索

卡密库支持输入客户卡密任意片段、尾号、绑定账号或完整激活链接；尾号重复时显示全部匹配卡密。每张卡提供复制充值链接、查看关联订单和复制 JSON。复制 JSON 优先取最新成功订单；没有成功订单时取最近一次提交，所选订单没有留存 JSON 时明确显示“未留存 JSON”。

从卡密库进入订单页时按客户卡密 ID 展示全部关联订单。订单页将客户兑换卡密与实际支付卡尾号分开显示，并可搜索客户卡密片段或支付卡尾号。历史 ZZS 独立卡密若仍有加密凭据则显示原卡密；无法恢复时标为“历史卡密未关联”，不把支付卡尾号误标为客户卡密。

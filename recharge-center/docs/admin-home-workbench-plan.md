# GPTC 后台首页功能盘点与工作台方案

盘点日期：2026-10-12。

状态：本文件记录功能盘点与首页设计要求。首页改版及此前的卡池直接加次数、订单解冻已合并实现，详情见 admin-home-workbench.md；生产发布结果以 GitHub Actions 的对应提交验证记录为准。

范围：后台首页 /admin（工作台），不是客户充值首页。根据当前分支的后台页面、按钮、服务方法和管理接口盘点；未读取生产凭据、订单或支付资料。保留现有业务处理规则，将操作入口集中到首页。

## 首页默认布局

1. 顶部状态栏：当前 Plus 通道、未停用支付卡的可轮选数量/次数、冻结次数、客户卡密未使用数量、待处理订单数量、最近更新时间。每个数量能筛选对应区域。API 仅显示配置/连接摘要，配置表单收进设置。
2. 正在使用的支付卡：显示未停用、未移出的支付卡。可用卡和需处理卡分别切换；不展示停用历史。列表行直接增加次数、解冻，录入卡按钮展开同页录入表单。
3. 最近订单：默认最近 10 笔，显示套餐、账号、客户卡密、支付卡尾号、状态、时间及操作。待处理标签独立展示全部未处理记录的数量，不受最近 10 笔限制。Plus、Pro 都纳入。
4. 最近客户卡密：默认最近生成的 20 张，可切换未使用、已使用、处理中/需核查，按套餐/销售渠道筛选。生成卡密、复制和导出均在此区完成。
5. 设置与更多工具：API、协议、Pro 自动配置及查询工具以同页折叠区或弹窗提供。历史库及完整日志保留独立页面入口。

录入支付卡和生成客户卡密是两套不同表单，明确区分。首次进入首页不自动生成卡密、不提交充值、不切换通道、不主动查询上游。

## 逐项功能安排

“行内”指列表里直接完成；“同页”指在首页展开、弹窗或抽屉内完成，不跳转其他页面；“专页”用于完整历史和诊断。

## 状态与联动要求

- 支付卡未停用但暂停、次数耗尽、余额不足、冻结或待核查，仍在首页“需处理”范围内。不能直接只筛剩余次数大于 0，否则最需要加次数的卡会消失。已停用、已移出支付卡不在首页默认列表和默认统计内。
- “可用卡数”与“当前可轮选次数”使用实际选卡规则，考虑占用、暂停、余额、Pro 保护及上游状态。剩余次数存在不等于当前可以轮选。首页与完整卡池需采用相同口径。
- 客户卡密的“未使用/已使用”来自卡密真实状态；订单失败不等于已使用。处理中、冻结待核查不冒充未使用可发放。卡密禁用与支付卡停用不是同一字段。
- 解冻支付次数、解锁客户卡密、增加支付卡总次数是不同操作，分别说明影响。不能因解锁旧失败订单而解锁该卡密较新的处理中/成功订单。
- 录卡或同步后刷新卡池和顶部；增加/解冻后刷新卡池、对应订单及统计；生成卡密后刷新本批和最近卡密；订单结案后刷新订单、相关卡密、支付卡与统计。
- 最近卡密/最近订单是展示窗口，不限制搜索和待处理提醒。较早的待处理订单不能被“最近 10 笔”截掉。筛选结果数、最近窗口数和全库数明确标注。
- 首页只显示操作适用的按钮。没有冻结不显示解冻；没有留存 JSON 不显示可复制按钮；Pro 使用自己的履约操作；已成功/已消耗的订单不显示解锁。
- 首页主列表摘要和详情按需读取。避免首次加载所有原始 JSON、完整返回历史和全部历史库。输入中、弹窗中保持选择和输入，不被自动刷新清掉。

## 实施与验收顺序

1. 集中卡池列表、录入、增量加次数、解冻；仅默认展示未停用卡。
2. 增加最近订单和待处理标签，所有日常处理在同页完成，日志折叠。
3. 增加最近客户卡密、生成、复制、导出和批量查询。
4. 整理通道/API/Pro 设置，使首页默认打开优先呈现运营操作。
5. 本地使用虚构资料完成端到端验证，完成次数去重、卡密与订单状态一致性、搜索/待处理全量范围及桌面/窄屏交互测试。
6. 上线时合并此前未发布的卡池修改；发布后只读验证线上页面和接口，确保实际网站可见。生产不拿真实卡做充值/解冻/加次数测试。

最终验收：管理员登录后台首页即可完成录入支付卡、加次数、处理冻结、生成/发放客户卡密、查看未使用和已使用卡密、查看并处理近期订单。查完整历史和深入诊断时才使用专页；首页不是只增加四个导航链接。
